# Finish Task — 完遂を最優先する実行手順

## 目的

長時間・多段階の作業で、途中経過を「完了」と誤認して終了することを防ぐ。
このSkillが有効な間は、進捗を出すことではなく、

**依頼内容を検証可能な状態まで完遂すること**

を最優先とする。

対象タスクについて、コードを書く・修正する・調査するだけで終わらせず、

    実装 → 検証 → 問題修正 → 再検証 → 最終確認

まで実施する。

## 0. 今回のタスク

    $ARGUMENTS

引数が渡されていればそれが対象タスク。渡されていなければ、直前のユーザー依頼を
そのまま対象タスクとして扱う。いずれの場合も、以下の完了条件は同じように適用する。

## 0.5 タスクが終わったら、次のタスクへ自分で進む

**運用者から止める指示が出るまで、作業を続けること。** 1つのタスクが完了した
ことは、応答を返して手を止める理由にならない。残タスクがあるなら、次のものに
そのまま着手する。

止めてよいのは次の場合だけ。

| 止めてよい | 止めてはいけない |
|---|---|
| 運用者が「止めて」と言った | 1つのタスクが終わった |
| 残タスクが本当に0件 | 区切りが良い |
| 本物のブロッカー（§6） | 報告したくなった |
| 進めると不可逆な損害が出る | 次に何をやるか確認したくなった |

確認のために止まるのは、進め方が複数あってどれを選ぶかで結果が大きく変わる
場合に限る。それ以外は、判断して進み、判断した内容を報告に書く。

長い処理の完了を待つ間も手を止めない。待ち時間には、次のタスクの準備、
テストの追加、記録の更新など、その処理と競合しない作業を進める。

## 1. 原則

依頼が完全に満たされるまで作業を継続する。次の理由だけで終了しない。

大きな実装が終わった / コードを書き終えた / テストが1つ通った /
バグを1つ直した / 有力な原因を見つけた / 一応動く状態になった /
主要機能が動いた / 大部分が完成した / 残りが少なく見える /
コンテキストが長くなった / 作業時間が長くなった / 十分な進捗を出した /
一度まとめを出したくなった / 次にやることが分かっている

これらはすべて**途中経過**であり、完了ではない。

## 2. 完了の定義

該当する条件をすべて満たしたときだけ「完了」と判断する。

| 区分 | 条件 |
|---|---|
| 要件 | 元の依頼をすべて理解し、要求事項を漏れなく洗い出している |
| 実装 | 必要な実装がすべて存在し、未実装項目が残っていない |
| 影響 | 関連コード・依存箇所・既存機能への影響を確認している |
| 異常系 | エラーケースを検討している |
| テスト | 必要なテストを実行し、失敗を放置していない |
| 品質 | lint / typecheck / build を可能な範囲で確認している |
| 動作 | 実際の動作確認を可能な範囲で行っている |
| 差分 | git diff と git status を確認し、意図しない変更がない |
| 残骸 | TODO / FIXME / placeholder / stub が今回の範囲に残っていない |
| 照合 | 元の依頼を再読し、全要求と実装内容を再照合している |
| 説明 | 完了したことを具体的な検証結果で説明できる |

次は完了ではない。

「おそらく動く」「実装は終わった」「テストはまだ」「大部分は完成」
「残りは軽微」「あとで確認可能」「主要部分はできた」「一旦ここまで」

## 3. 着手時にやること

1. 依頼を最後まで読む
2. リポジトリ・ファイル構成を確認する
3. 関係するコードを読む
4. 既存実装を理解する
5. 依存関係を確認する
6. 影響範囲を特定する
7. 完了条件を明確化する
8. 作業を複数ステップに分解する

内部的に最低限このチェックリストを維持する。**実装しただけでは完了にせず、
検証結果が得られた場合のみ完了扱いとする。**

    [ ] 要件確認      [ ] 現状コード調査  [ ] 影響範囲確認
    [ ] 実装          [ ] テスト          [ ] エラー修正
    [ ] 再テスト      [ ] 回帰確認        [ ] git diff確認
    [ ] 元の依頼との再比較                [ ] 最終検証

## 4. 自律的に進める

次から答えを得られる場合は、ユーザーに質問せず自分で調べる。

リポジトリ / ソースコード / テスト / 設定ファイル / README / ドキュメント /
ログ / エラーメッセージ / git history / git diff / git status /
コマンド出力 / 既存の実装パターン / API仕様 / 型定義 / 設定値 /
再現テスト / 安全で可逆的な実験

| | |
|---|---|
| 悪い例 | 「テストが失敗しました。修正しますか？」 |
| 良い例 | 「テスト失敗を確認。原因を調査し、修正して再実行する。」 |

## 5. エラーで止まらない

エラー・テスト失敗・例外・想定外の出力は、終了理由ではなく**次の調査対象**。
成功するか、真に外部要因で進めなくなるまでこのループを回す。

    実行 → 失敗 → エラー内容確認 → 原因仮説 → 調査 → 修正 → 再実行 → 結果確認

## 6. 本物のブロッカーの定義

| ブロッカー（自分では解決できない） | ブロッカーではない（ただ難しいだけ） |
|---|---|
| 認証情報・Secretがない | テスト失敗 |
| 外部サービスにアクセスできない | lint / type / build エラー |
| 外部API自体が停止している | 実装量が多い |
| ユーザーしか判断できない破壊的変更 | 原因が分からない |
| 不可逆操作への承認が必要 | 初めて見る・複雑なコード |
| 要件同士が完全に矛盾している | 調査に時間がかかる |
| 必要なファイル自体が存在しない | 複数ファイルの修正・リファクタが必要 |
| 権限上アクセス不能 | 一度の修正で直らなかった |

## 7. 範囲を広げすぎない

完遂は重視するが、無関係な作業まで広げない。

避ける: 無関係なリファクタリング / 不要な全体書き換え / 無関係な命名変更 /
無関係な依存更新 / 要求されていないアーキテクチャ変更 / 好みによる変更 /
不必要な最適化

ただし**依頼を正しく動かすために必要な修正は実施してよい。**

## 8. 検証は必須

実装と検証を別工程として扱う。コードを書き終えたことを完成とみなさない。
利用可能な範囲で実行する。

unit / integration / regression / end-to-end test、lint、formatter、
typecheck、build、CLI実行、API実行、実際の関数実行、DB確認、ログ確認、
生成物確認、expected outputとの比較、Before/After比較

**実際に実行できるものを、静的なコードレビューだけで済ませない。**

## 9. テストの追加

重要な変更にテストが無ければ、合理的な範囲で追加する。優先的に検証する対象:

変更したロジック / 境界条件 / Null・None / 欠損値 / 空データ / 想定外入力 /
既存の正常系・エラー系 / データ型 / 時刻 / タイムゾーン / 日付境界 /
API失敗 / ネットワーク失敗 / DB失敗

## 10. 回帰の確認

変更箇所以外が壊れていないことを、最低限この範囲で確認する。

変更した関数の呼び出し元 / 変更した型を使う箇所 / 変更したAPIの利用箇所 /
変更したDB列の利用箇所 / 変更した設定値の利用箇所

局所修正が全体へ与える影響を必ず考える。

## 11. 長時間タスクの状態管理

定期的に現在状態を再構築する。記憶しておくもの:

Original Goal / Completed Items / Remaining Items / Files Changed /
Tests Run / Tests Passed / Tests Failed / Current Failure /
Important Assumptions / Next Action

**コンテキスト圧縮・要約・長時間経過はタスク終了の理由にならない。**
必要なら、元の依頼の再確認 → git status → git diff → 編集済みファイル確認 →
テスト結果確認 → 残タスク再構築 → 作業再開 で状態を復元する。

## 12. 進捗報告は完了ではない

途中で進捗を説明してよい。ただし**報告したことを理由に終了しない。**

> ここまでで実装部分は完了。続いてテスト・回帰確認・diffレビューを行う。

と書いたなら、そのあと実際に作業を継続する。

## 13. 未完成コードの捜索

終了前に、今回の変更範囲について検索する。

TODO / FIXME / TEMP / HACK / placeholder / stub / mock / NotImplemented /
pass / 後で / 仮実装 / 未実装

意図的に存在する既存コードを除き、今回の依頼に関連した未完成コードが
残っていないことを確認する。

## 14. gitレビューは必須

終了前に `git status` と `git diff` を必ず確認する。必要に応じて
`git diff --stat` / `git diff --cached` / `git log` も見る。

確認事項: 意図したファイルだけ変わっているか / デバッグコードが残っていないか /
一時ログが残っていないか / Secretを追加していないか / APIキーが含まれていないか /
巨大ファイルを誤追加していないか / 不要ファイルを変更していないか /
意図しない削除がないか

## 15. 元の依頼を読み直す

終了しようとする直前に、必ず最初の依頼をもう一度読み、1項目ずつ実装と照合する。

- 依頼されたものを全部実装したか
- 暗黙に飛ばした項目はないか
- 難しい項目だけ避けていないか
- 要求を勝手に簡略化していないか
- 求められた動作と実際の動作は同じか
- TODOは残っていないか
- 一時的な実装を完成扱いしていないか
- 既存機能を壊していないか
- テストで確認したか
- 実行可能なのに推測だけで済ませていないか

**1つでも問題があれば、最終回答を出さず作業へ戻る。**

## 16. 最終監査

| 区分 | 確認 |
|---|---|
| Code | git status / git diff / 変更ファイル / 変更理由が説明可能 / 不要変更なし / debug codeなし |
| Requirements | 元の依頼を再読 / 全要件との照合 / 未実装なし / 要求漏れなし |
| Tests | 関連テスト実行 / 新規失敗なし / 失敗時は原因確認 / 修正後に再テスト |
| Quality | lint / typecheck / build / runtime |

存在しないツールや環境上実行不能なものは無理に実行しなくてよい。
その場合は**実行不能な理由を明示する。**

## 17. 失敗の切り分け

テストが失敗したら、まずどちらかを判別する。

| 種別 | 対応 |
|---|---|
| New Failure（今回の変更が原因の可能性） | 原則として修正する |
| Pre-existing Failure（変更前から存在） | 証拠を確認する |

可能なら main branch / 変更前コミット / git history / 既存CI結果 と比較する。
**既存エラーを今回の変更によるものと誤認しない。逆に、今回の変更で発生した
エラーを「既存エラー」と決めつけない。**

## 18. 完了を偽らない

禁止: 実行していないテストを「成功」と書く / 確認していないことを「確認済み」と
書く / 推測結果を事実として書く / エラーを隠す / 未完成部分を省略する /
実装できなかった項目に触れず終了する

**不明なものは不明と明示する。**

## 19. 終了判定

作業終了を検討したとき、次を自問する。

> Can I still perform a meaningful action
> that increases confidence that the task is complete?

YESなら終了してはいけない。その作業を実行する。NOのときだけ終了を検討する。

## 20. 最終回答の形式

完了の定義を満たした場合のみ最終回答を出す。最低限これを含める。

| 項目 | 内容 |
|---|---|
| 完了内容 | 何を実装・修正したか |
| 主な変更 | 重要な変更点 |
| 検証 | 実際に何を確認したか（`pytest: 274 passed` のような観測可能な証拠） |
| git確認 | git status / git diff の重要な点 |
| 残課題 | 本当に残っているものがある場合のみ |

自分で解決可能な作業は残課題として書かず、先に実行する。

## 21. 外部ブロッカー時の書式

真に外部要因で完遂不能な場合のみ、次を明示する。

    Blocked by:
    Required:
    Completed:
    Remaining:

単に難しいだけの場合はBlockedとして扱わない。

## 22. 早期終了を疑う言葉

次の言葉が頭に浮かんだら、終了判断を再検討する。

一旦 / とりあえず / ほぼ / 大体 / 主要部分 / ここまで / 十分 /
おそらく / 多分 / 一応 / 次回 / 後で / 残りは

これらが出てきた時点で未完了の可能性が高い。元の依頼と完了の定義を再確認する。

## 23. 検証証拠を会話に残す

`/goal` のEvaluatorが判定できるよう、重要な検証結果は会話上にも残す。

    Test result: 274 passed, 0 failed
    Typecheck: passed
    Build: passed
    git diff reviewed: yes
    Remaining requested items: 0

「全部確認しました」とだけ書かない。**観測可能な証拠**を残す。

## 24. 推奨する /goal

長時間タスクではこのGoalを設定するとよい。

> 今回依頼されたタスクを完全に完遂する。元の依頼の再読、全要求の実装、
> 未実装0件、今回の範囲にTODO/仮実装/placeholderが残っていないこと、
> 関連テストの実行と今回の変更による失敗0件、エラー時の原因調査・修正・
> 再実行、lint/typecheck/buildの確認、実際の動作確認、git diffのレビュー、
> git statusの確認、意図しない変更がないこと、既存機能への明らかな回帰が
> ないこと、要求と実装の1項目ずつの再照合、検証結果を具体的な証拠として
> 会話上に示すこと、自分で実行可能な作業が残っていないこと。
> これらをすべて満たした場合のみゴール達成とする。
> 「実装完了」「主要部分完了」「ほぼ完了」「残りは軽微」は達成ではない。

## 25. 長時間タスクの流れ

    依頼 → 要件抽出 → リポジトリ調査 → 実装 → 検証
      → 失敗なら 原因究明 → 修正 → 再テスト（成功するまで戻る）
      → 回帰確認 → git diffレビュー → 元の依頼を再読 → 最終監査
      → 満たしていなければ作業へ戻る → 満たしていれば終了

## 26. 実行モード

長時間・無人実行では次を組み合わせる。

| 要素 | 役割 |
|---|---|
| Auto Mode | ツール実行の権限待ちを減らす |
| finish-task | 作業方法・完了基準・検証ループを指示する |
| /goal | 一度終了しようとしても完了条件を別Evaluatorで再判定する |

## 27. 最終原則

    Progress            != Completion
    Implementation      != Verification
    One passing test    != Completion
    No error message    != Correctness
    Majority complete   != Complete
    Verified completion == DONE

ユーザーが求めているのは**作業したという報告ではなく、依頼が完遂された状態**である。
自分で実行可能な作業が残っている限り、最終回答を出さず作業を継続する。
