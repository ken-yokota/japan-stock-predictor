# 失敗記録: 過去日（8/3〜8/7）の本番再現

2026-08-11。5営業日を本番として再現する作業で、6回連続して失敗した。
1日も完走していない。

原因は毎回違う場所だが、**同じ1つの不変条件が6層で守られている設計に対し、
1層ずつ穴を開けようとした**という一点に集約される。

---

## 何をしようとしたか

過去の営業日について、その日より前のデータだけで予測を計算し、ライブの
予測テーブルに保存して、通常のダッシュボードタブに表示する。

前提として、この仕組みには2つの保護がある。**片方だけが先読み防止**である。

| 保護 | 意味 | 過去日で |
|---|---|---|
| `available_timestamp <= cutoff` | その値が判断時点で市場に存在したか | **成立する。緩めてはならない** |
| `first_observed_at / retrieved_at <= cutoff` | このシステムが当時取得済みだったか | 成立しない（後から取得したため） |

2つ目は「先読み防止」ではなく「**ライブ実績である証明**」である。緩めても
予測の正当性は損なわれず、ライブ実績と名乗れなくなるだけ。そこで
`--backfill` を作り、2つ目だけを外す方針を取った。

方針そのものは正しかった。実装の進め方が誤っていた。

## 失敗の一覧

| 回 | 落ちた場所 | エラー | 到達時間 |
|---|---|---|---|
| 1 | 容量削減の設計 | （発生前に停止） | 書き込み前 |

### 1. 容量削減が過去日で機能しない設計

`prune_feature_history` は「直近2つの**予測日**を残す」判定だった。8/3を再現
すると、8/11・8/10より古くソートされるため**書き込み前に何も削除されない**。
残り131MBのデータベースに133MBを書きに行く状態だった。

3分経過時点で気づき、DiskFullが起きる**前に**実行を停止した。判定を
「直近2回の**実行**を残す」（`max(generated_at)` 順）に変更。再現した日は
最近の実行なので自分の行を保持し、代わりに最も古く生成された日が消える。

> **教訓**: 保持ポリシーの並び順は、その値が何を意味するかで決まる。
> 「直近N日」と「直近N回の実行」は、過去を扱った瞬間に別物になる。

### 2. SQLiteでは通りPostgreSQLで落ちるSQL

上の修正で書いたクエリが、PostgreSQLの構文規則に違反していた。

```sql
SELECT DISTINCT prediction_date ... GROUP BY prediction_date
ORDER BY max(generated_at) DESC
-- ERROR: for SELECT DISTINCT, ORDER BY expressions must appear in select list
```

SQLiteは受け付けるため、**テストは283件すべて緑**だった。5営業日とも10秒で
死んだ。`GROUP BY` が既に1行ずつ返すので `DISTINCT` は冗長であり、集計を
select列に入れて解決。

このリポジトリがSQLite/PostgreSQLの差に噛まれたのは**2回目**である。1回目は
1行ごとのINSERTがSQLiteでは無害に見えて、本番では1銘柄91,356文・22銘柄で
63時間になっていた件。

> **教訓**: 本番だけが実行するクエリには、本番と同じエンジンのテストが要る。
> 対策として、ローカルにPostgreSQLがあれば実機で走るretentionテストを追加した。

### 3〜5. 同じ検査の写しが保存層に3つ

`--backfill` を**特徴量の構築側にしか通していなかった**。保存層には同じ検査の
写しが3つあり、特徴量を7〜10分かけて作った後、書き込む段階で毎回弾かれた。

| # | 場所 | 検査内容 |
|---|---|---|
| 3 | `add_feature_input` | 来歴行1本ごとに観測時刻を検査 |
| 4 | `add_feature_input` | スコア行と walk-forward セットには、より厳しい締切で再検査 |
| 5 | `finalize_feature_set` | セット全体の `max(first_observed_at)` を集計して検査 |

さらに5回目は、私が修正した関数に**呼び出し側が引数を渡していない**という
別のミスだった。関数の側だけ直して「通した」つもりになっていた。

> **教訓**: 1箇所直して実行、を繰り返してはいけない。最初に
> `grep -rn "first_observed_at\|retrieved_at"` で全箇所を洗い出し、
> 揃えてから実行すべきだった。

### 6. スキーマのCHECK制約

```sql
CHECK (max_first_observed_at IS NULL OR max_first_observed_at <= cutoff_at)
-- name: ck_feature_sets_observed_cutoff
```

無条件。緩めるには migration が必要で、**ライブの行を含む全行**でこの保証が
失われる。

**緩めなかった。** この制約は「`feature_sets` のどの行も、実際には持って
いなかった観測を主張していない」ことをデータベース側で検証可能にしている。
過去日をダッシュボードの通常タブに出したいという便宜のために外すのは割に
合わない。この種の保証は、外しても誰も気づかず、気づいたときには手遅れになる。

> **教訓**: 6層で守られているという事実自体が設計の意図である。
> 2層目で気づくべきだった。

## 進め方の誤り

失敗の中身より、こちらのほうが再発しやすい。

| 誤り | 正しくは |
|---|---|
| 1箇所直して実行、を繰り返した | 最初に全箇所をgrepして、揃えてから実行する |
| SQLiteのテスト緑を「通った」と読んだ | 本番だけが実行するクエリは本番のエンジンで試す |
| 引数を誤った位置に挿入して構文エラーを作った | 挿入後に `python -c "import ast; ast.parse(...)"` で確認する |
| 実行中の pytest を `pkill` で巻き込み、失敗/ハングと誤読した | プロセスを撃つ前に何が動いているか確認する |
| 「過去日は予測不可」と誤って報告した | 2つの保護を混同していた。指摘を受けて訂正 |

## 正しい経路

リポジトリには**この用途のために作られた経路が既にある**。

- `services/dataset.py` の `build_backtest_frame` — 結果を `ESTIMATED_BACKFILL` と
  明示的にラベルする
- `backtest/walk_forward.py` と `scripts/run_walk_forward.py`
- ダッシュボードの Backtest タブ（`pages/5_Backtest.py`）

過去日はライブの予測テーブルではなく、こちらに置くのが設計の意図である。

## 残っている loose end

現在の main には `--backfill` フラグが残っているが、**DB制約に阻まれて動かない**。
コードは通るのに最後で必ず落ちる。次に触る人が同じ9分を無駄にする。

対処は2択。

| 案 | 内容 |
|---|---|
| A | フラグを削除し、過去日は walk-forward 経路のみとする（素直） |
| B | フラグを残し、DB制約に当たることを docstring とテストに明記する |

## 副次的に判明したこと

この作業の過程で、本番の予測が初めて完走するようになった。

| 対象 | 前 | 後 |
|---|---|---|
| DB往復（1銘柄） | 91,356文 | 48文 |
| 特徴量構築（22銘柄） | 22.5分 | 6.6分 |
| 1回の朝の書き込み | 156 MB | 133 MB |
| 取得の成功系列 | 0 / 54 | 51 / 51 |

また、朝13分21秒のうち **特徴量構築49%・保存41%** で、**データ取得は1%**しか
占めていないことが実測で分かった。特徴量構築の43%は `_utc()` を694万回
呼んでいる分で、同じ行の同じタイムスタンプを121回×22指標ぶん変換し直して
いる。読み込み時に一度だけ正規化すれば 6.6分 → 3〜4分 の見込み（未実施）。
