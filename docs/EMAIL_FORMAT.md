# メール形式（承認済み）

> **実装は `notifications/report_layout.py` にある。**
> 予測メール・結果メール・進捗メールはすべてこのモジュールで組む。
> HTMLを手書きしない。進捗メールは `scripts/send_status_report.py` に
> JSONを渡して送る。読みやすさを人の心がけではなくコード経路の性質にする、
> というのがこの構成の目的。


2026-08-11に運用者が承認した形式。予測メール・結果メール・進捗メールの
3種類すべてに適用する。**この形式から外れたメールを送らない。**

承認の経緯: それ以前の形式は「とても見づらい」との指摘を受け、
1銘柄1ブロックの箇条書きから、色付きHTMLの表に作り直したもの。

---

## 全メール共通の骨格

| 要素 | 仕様 |
|---|---|
| 本文 | HTMLを主とし、text/plainを代替として必ず添える |
| 幅 | `max-width:680px`、中央寄せ、白地カードに角丸 |
| 表 | `overflow-x:auto`で囲む。スマホで横スクロールできること |
| 見出し | 左に4pxの縦罫、16px |
| リード文 | 見出し直下に1行。件数・合計・ルールなど要点だけ |
| 末尾 | 免責または「操作の要否」を1行 |

### 色

| 用途 | 色 | 使いどころ |
|---|---|---|
| 上昇・成功 | `#15803d` | プラスのリターン、的中、完了 |
| 下落・失敗 | `#b91c1c` | マイナスのリターン、外れ、上限到達 |
| 本文 | `#111827` | 通常の文字 |
| 補助 | `#6b7280` | 単位、理由、参考値 |
| 表の見出し | 背景 `#1f2937` / 文字 白 | ヘッダ行 |
| 強調行 | 背景 `#ecfdf5` | 買い候補、完了項目 |
| 交互の縞 | 背景 `#f9fafb` | 長い一覧の可読性 |

**数値の符号は必ず色を付ける。** 符号だけでは電話で読み取れない。

## 1. 予測メール

件名: `【日本株AI予測】YYYY-MM-DD 寄り付き→大引け／買いN銘柄`

リード文には、判定ルール（予測リターンの閾値と上昇確率の閾値）を必ず入れる。
なぜその銘柄が選ばれなかったのかが、ルールなしでは読めない。

| 順 | セクション | 列 |
|---|---|---|
| 1 | 買い候補 | 順位・銘柄・予測リターン・上昇確率・前日終値・予測終値 |
| 2 | なぜその予測になったか | 銘柄ごとに寄与の大きい要因4つ（寄与・要因） |
| 3 | 全銘柄 | 銘柄・判定・予測リターン・上昇確率・前日終値 |
| 4 | 注意 | 優位性未確認の明記、取得状態の但し書き |

セクション2が運用者の要望の中心。特徴量の内部名ではなく日本語にする
(`us_10y_minus_2y_spread__return_20d` →「米10年-2年金利差の20日リターン」)。
寄与はモデルの計算そのもので、全要因の合計と切片が予測値に一致する。

セクション3は買わなかった銘柄も含めて全件出す。欠けている銘柄が
「予測がない」のか「載っていないだけ」なのかを区別できるようにするため。

## 2. 結果メール

件名: `【日本株AI結果】YYYY-MM-DD 答え合わせ／買いN銘柄 X勝Y敗 ±Z円`

件名だけで勝敗と損益が分かること。運用者は本文を開かずに判断する。

| 順 | セクション | 列 |
|---|---|---|
| 1 | 本日の成績 | 区分・銘柄数・方向的中・平均実績・合計損益（買い/全銘柄の2行） |
| 2 | 買った銘柄の結果 | 銘柄・予測・実績・的中判定・始値→終値・損益（損益順） |
| 3 | 買わなかった銘柄 | 銘柄・予測・実績・見送りの理由（実績順） |
| 4 | この数字が示していないこと | 標本数の限界を必ず書く |

セクション3の「見送りの理由」は、どの閾値に何%足りなかったかまで書く
（「確率が58%で閾値未満」）。「NO_BUY」だけでは判断を再現できない。

セクション4は削らない。1日5取引の結果を成績として読ませないための節。

判定（的中・外れ）は**方向**についてのもので、損益の正負とは一致しないこと
がある。予測+1.0%に対し実績+0.2%なら方向は的中で、手数料込みの損益は
マイナスになりうる。表はその2つを別の列に置く。

これらの表の実装は `notifications/result_report.py` にあり、下の大引け後
メールと**同じ関数**から組まれる。片方だけが読みやすい状態に戻らないように
するための構成。

## 2-1. 大引け後メール（毎営業日 17:00 JST・運用者が実際に毎日受け取るもの）

件名: `【大引け後】YYYY-MM-DD 買いN銘柄 X勝Y敗 ±Z円／要確認M件`

実績が確定していない日は
`【大引け後】YYYY-MM-DD 実績が確定していません／要確認M件`。
**結果が出ていない日ほど届く必要がある**ので、行がないことを理由に送信を
やめない。

| 順 | セクション | 列 |
|---|---|---|
| 1 | できなかったこと | 何が・なぜ・どう対処したか・いまどうなっているか |
| 2 | 本日の成績 | 区分・銘柄数・方向的中・平均実績・合計損益 |
| 3 | **図: 本日の予測と実績** | 銘柄・予測・実績・図 |
| 4 | 買った銘柄の結果 | 銘柄・予測・実績・判定・始値→終値・損益 |
| 5 | 買わなかった銘柄 | 銘柄・予測・実績・判定・見送りの理由 |
| 6 | **図: 直近N営業日の損益と累積** | 日付・買い・日次損益・累積・図 |
| 7 | **図: 方向的中率の推移** | 日付・的中・的中率・図 |
| 8 | この推移が示していないこと / この数字が示していないこと | 標本数を必ず添える |
| 9 | できたこと | 内容・確認した証拠・状態バッジ |
| 10 | 本日の実行状況 | 工程・状態バッジ・所要・内訳 |
| 11 | データの健全性 | 項目・値（EOD行数、スナップショット、当日取り込み、DB使用量） |
| 12 | 研究: 予測要素の採否 | 比較・判定（INVALIDは赤） |

**セクション1が先頭であることが要件。** 成功だけを並べた報告は報告ではない。
失敗が0件の日も節ごと消さず「本日は検出された失敗はありません」と書く。
節が消えると、失敗がなかったのか確認しなかったのかを区別できない。

失敗として必ず拾うもの:

| 検出 | 出す内容 |
|---|---|
| runが SUCCESS 以外 | 状態・失敗した系列名・後続にどう影響したか |
| 実行記録そのものが無い | どの工程が本日走っていないか |
| 予測セットが無い / READY でない | 採用判断に使えないことを明記 |
| 実績が全銘柄で確定していない | 予測N件に対し確定M件、と両方の数 |
| 当日取り込みが0行 / スナップショット0件 | どの系列が予測に入っていないか |
| DB使用量が上限の85%超 | 上限に達した朝は書き込みが止まる旨 |
| 研究成果の INVALID | まとめて1行。p値は引用しない |

同じ失敗が複数回記録された場合（リトライは別runになる）は1行にまとめ、
`（3回）` と回数を付ける。同じ文が3行並ぶと、その日の他の失敗が
スマートフォンの画面から押し出される。

DBが読めない・接続できない場合も**送信する**。読めなかったこと自体を
セクション1の1行目に出す。届かない報告より、不完全な報告のほうが役に立つ。

### 図

実装は `notifications/report_layout.py` の `diverging_bar` / `stacked_bars` /
`ratio_bar` / `legend`。**入れ子テーブルの背景色で描く。**

| 使わないもの | 理由 |
|---|---|
| `<svg>` | Gmailが要素ごと削除する |
| `<img>`（外部URL） | Gmailが既定でブロックする |
| `background-image` | 同上、Outlookでも落ちる |
| CSS flex / grid | Outlookが解釈しない |

図が空白で届くのは、図が無いより悪い。行だけが「図がある」と主張するため。
テストが `<svg` `<img` `src=` `background-image` の不在を確認している。

図の規則:

- **1つの図の全行は同じ目盛りで描く。** 行ごとに縮尺が変わる図は嘘をつく。
  基準はその列の絶対値の最大。
- **発散バーは中心線から。** 右が利益、左が損失。ゼロは棒を描かない。
- **予測の棒は緑でも赤でもない**（`FORECAST` のスレート）。予測は主張であって
  結果ではなく、結果の色を付けると結果として読まれる。
- **色は必ず凡例で名前を付ける。** 説明のない色は装飾。
- **的中率は50%を基準に色を変える。** 基準線を図中に引くと落ちる客先がある
  ため、比較は色が運び、閾値は列見出しに書く。
- 推移の図には**標本数を書いた注記**を必ず添える。「10営業日・買い46取引の
  累積で -64,818円」のように、数字と標本を同じ文に置く。

### 毎回届くこと

運用者の要件は「毎回送る」。片方だけでは満たせないので両方を実装する。

| 失敗 | 対策 |
|---|---|
| cronが発火しない（2026-08-12に実例） | 17:00 / 17:20 / 17:40 JST の3本 |
| 3本とも送ってしまう | `email_logs` に日付キーで記録し、送信済みならスキップ |
| 報告の組み立てが落ちる | 「組み立てられませんでした」というメールを送る |
| 3本とも発火しない | `delivery_watchdog` の夕方チェックが SENT記録の不在を検出 |

冪等キーは `daily-summary-YYYY-MM-DD`。`--force` で上書き送信できる。
DBが読めない日は重複判定ができないので**送る側に倒す**。届かないことで
異常を伝える設計にはしない。

監視は 18:00 / 18:20 JST で、最後の再試行（17:40）より後に判定する。
再試行中のものを失敗と報告しないため。

## 3. 進捗メール

件名: `【進捗 n/m】...` — 分数を件名に必ず入れる。

| 順 | セクション | 列 |
|---|---|---|
| 1 | この報告の要点 | 表が運べない一文（新しい依頼が何を後ろ倒しにしたか等） |
| 2 | いま進めているタスク | 工程・内容・想定・経過・状態 |
| 3 | 今後の予定 | 時刻・内容・詳細 |
| 4 | 本番の最新状態 | 項目・値 |
| 5 | 直近の自動実行 | ジョブ・結果・開始 |
| 6 | コードの状態 | 項目・値 |

状態はバッジで示す（実行中は青、完了は緑、待機は灰、警告は橙、失敗は赤）。

件名は `【進捗 n/m】<実行中の工程名>／定期報告 MM/DD HH:MM`。
分数は必須。`【進捗】` だけでは、運用者はロック画面で自分の依頼が
どこまで進んだかを判断できない。

**すべて送信時に読み直す。** 工程表は `.progress-tasks.json`、経過は各工程の
`started_at`、本番の状態はDB、自動実行はGitHub Actions、コードはgit。
記憶や、以前書いたメモから組まない。工程表はそれ自体の更新時刻を持ち、
`--stale-after` 分を超えたら「⚠ この記録は◯分前のもので更新されていません」
と書く。古い記録を現在の状態として出さないため。

「いま進めているタスク」の注記には**残り想定と完了予定時刻**を必ず入れる。
実行中の工程が想定を超えたら
「⚠ 3/7 は想定20分に対し35分経過しています。失敗ではなく、まだ実行中です」
と本文で名指しする。想定が出せない工程は0分として合算せず、
「うち1工程は想定を出せていません」と書く。

「今後の予定」の時刻は `scripts/send_progress_report.py` の `SCHEDULE` にあり、
各workflowの先頭cronをJSTに直したもの。テストが workflow ファイルと突き合わせる
ので、片方だけ変えると落ちる。GitHub Actions のcronは実測で30〜60分遅れて
起動するため、その旨も注記に入れる。

進捗メールの送信規則（頻度・1工程1通・表の使用）は
`.claude/skills/working-agreements/SKILL.md` と
`.claude/skills/email-status-reports/SKILL.md` にある。
本書はその見た目を定める。
