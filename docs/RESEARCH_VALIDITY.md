### 無効とする理由

いずれも「測定が雑だったから」ではなく、**測っている対象が本番と違うから**です。

1. **本番経路と研究経路で、特徴量とデータ取得経路が一致していない。**
2. **特徴量数が一致しない。** 本番は業種別に約103〜169、研究経路は25〜78。
3. **データ経路が一致しない。** 研究はYahoo日足を直接取得する。本番はDB経由で
   Provider選択・品質ゲート・PIT lineage・Adjusted Close優先を通る。
   研究経路の日経先物は `NKD=F`、本番snapshotは `NIY=F` で、銘柄自体も違う。
4. **07:00取得と08:30鮮度判定の矛盾が未解決。** 本番ではFX(許容10分)・
   先物(20分)・商品(40分)が stale 扱いで除外されている可能性がある。
5. **したがって、本番相当のOOS性能としては解釈できない。**

`window250.json` にはさらに固有の理由があります。交差検証のfoldごとに重み合計が
学習件数へ再正規化されておらず、alpha選択時の実効正則化がfold間で最大4.5倍
ばらついた状態で測定しました (fold1: 45件に対し重み合計10.05 / fold5: 209件に
対し150.12)。手続きは `01d19d6` で修正済みで、baseline対baseline@hl60 は
修正後に再測定して結果が同一 (p=0.946) であることを確認しています。
focused系2件は未再測定です。

### 使用条件

- **数値は再現性のため保持する。**
- **採用判断および本番性能の評価には使用しない。**
- **本番経路での再測定が済むまで、この結果を根拠に設定・特徴量・モデルを
  変更しない。**

### 検出力: これらの結果は「効果なし」ではなく「判定不能」でした

2026-08-09 に実測した結果です。

| | 値 |
|---|---|
| 検証期間 | 49営業日 / 全予測 1,078件 |
| 同日22銘柄の級内相関 | 生データ 0.082 / 不一致ペア 0.348 |
| ペアリング後の実効サンプル | 約101件 |
| **検出可能な効果** | **方向的中率で約3.1pp** |

下表の4案はいずれも +0.19〜+0.93pp で、**検出限界の1/3以下**です。

したがってこれらを「有意差なし」と報告したのは不正確でした。正しくは
**「この検証基盤では判定できない」**です。真に有効な施策と真に無効な施策が、
同じ p ≈ 0.6 として返ってきます。

次に施策を測る前に、**期待される改善幅が検出限界を超えているか**を先に
確認してください。超えないなら、その実験は何も答えません。検出力そのものを
上げる施策（期間の延長、市場ベータを除く横断面化、符号検定ではなく Rank IC）
のほうが先です。

### 参考: 測定された内容そのもの

再測定の設計に使うためだけに残します。**性能の証拠ではありません。**

| 試したこと | 方向的中率の差 | 符号検定 p |
|---|---:|---:|
| 予測要素 25 → 44 (focused) | +0.74pp | 0.602 |
| 予測要素 25 → 78 (extended) | +0.83pp | 0.638 |
| 学習窓 120日 → 250日 | +0.93pp | 0.563 |
| 直近重視 (半減期60営業日) | +0.19pp | 0.946 |

いずれも有意差なし。**この期間・この経路では、どの案も採用に至りませんでした。**

あわせて、これらの測定中に判明した事実を2つ記録します。どちらも再測定でも
そのまま問題になります。

- **ハイパーパラメータが探索範囲の境界に張り付いている。**
  Ridge alpha は 1,078予測すべてで候補上限の 100.0、Logistic C は候補下限の
  0.01 が選ばれた (学習窓250日では 100.0%)。交差検証が用意した範囲より
  強い正則化を求めており、モデルが特徴量をほとんど信用していない。
- **naive baseline を下回った期間がある。**
  2026-07-01〜08-07 の実際の上昇比率は 57.07%、モデルの方向的中率は 54.38%。
  「常に上昇と予測する」だけの基準に負けている。

## 現行本番は無変更

このセッションで、本番の**モデル・設定・特徴量・スケジュールは変更していません**。

変更前のコードを git から取り出し、同一データで学習して全出力を突き合わせて
確認済みです。Ridge係数・切片・alpha・C・学習本数・定数確率・予測リターン・
上昇確率がすべて完全一致しました。Logistic係数のみ 5.2e-18 の差が出ましたが、
変更前のコードを2回実行しても同じ差が出るため liblinear 固有の非決定性であり、
変更に起因しません。

## 12系列が届いていない理由（2026-08-09 診断）

当初「07:00取得と08:30鮮度判定の矛盾」が原因と考え、P0として記録しました。
実際にコードとDBを確認した結果、**その矛盾はまだ一度も発現していません**。

```
market_data の interval 内訳:  eod のみ 16,357件
interval='live_snapshot' の行:  0件
daily_runs:                     1件（手動bootstrap、status=PARTIAL）
```

`services/dataset.py` はこの12系列を `interval == 'live_snapshot'` の行から
探しますが、その行が1件も存在しません。`services/ingestion.py:98` は
`include_snapshots=True` を渡しており、**コードは正しい**。単に
**朝のpipelineが一度も完走していない**ため、スナップショットが取得された
ことがないだけです。

2026-08-10 07:00 が初回実行です。そこで初めて `live_snapshot` 行が生まれます。

ただし懸念は残ります。07:00取得の値は08:30 cutoff時点で90分経過しており、
許容は FX 10分 / 先物 20分 / 商品 40分 です。**初回実行の結果で、
本当に落ちるのかが判明します。** それまでは推測です。

なお、仮に修正しても即座には使えません。コードのコメント通り、スナップショット
特徴量は日次観測が蓄積されてから学習に入ります。120営業日ぶんで**約6ヶ月**です。
意思決定を6ヶ月待たないために、研究経路（`research/`、Yahoo直接取得）で
12系列入りのBaselineを先に作る道があります。

## 次回の再開点

### P0. 予測時刻の契約を統一する

- morning prediction は 08:20 実行とし、原則 `prediction_timestamp` を
  08:20 JST とする。
- 全特徴量で `available_timestamp <= prediction_timestamp` を保証する。
- 「08:30時点」という表現との矛盾を解消する。ドキュメント・docstring・
  config・workflow のどこが正なのかを1箇所に決める。
- 海外市場の確定値と、直前のFX・先物スナップショットを**分離して取得**する案を
  検討する (増分EOD取得を早朝、snapshot+予測を08:20〜08:29の短いjobへ)。

### P1. FX・先物が実際に除外されているかを事実確認する

**まだ修正しない。** ログ・DB・provider_status から、対象日・取得時刻・
`available_timestamp`・staleness・採否理由を一覧化するところまで。
推測ではなく観測で確定させる。

### P2. naive baseline との厳密な Walk-Forward 比較

同一OOS日・同一銘柄で対比較する。

- always-up (常に上昇)
- 過去上昇率
- 直前日方向 (前日方向継続)
- zero-return 予測

評価は全銘柄方向精度だけでなく、**BUY条件適用後および Top-N** の
Win Rate / Net Expectancy / Profit Factor / 最大ドローダウン / Spearman相関を含める。
統計検定は銘柄行を独立とせず、**日付単位の block bootstrap** を使用する。

### P3. ハイパーパラメータ探索範囲の拡張と境界張り付きの再検証

- alpha に 100 より大きい範囲を追加する。
- C に 0.01 より小さい範囲を追加する。
- fold内の重み合計を学習件数へ正規化した状態で実行する (`01d19d6` で修正済み)。
- 性能改善だけでなく、**係数がどこまで縮んでいるか**も確認する。

### P4. 研究経路と本番経路の統一

同じ snapshot / 同じ特徴量生成 / 同じ欠損・鮮度判定 / 同じ学習・評価コード /
同じモデル設定。統一後に P2 をやり直して初めて、本番相当のOOS性能になる。
