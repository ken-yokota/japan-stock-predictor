# 予測値の計算過程

更新日: 2026-08-09

朝の予測が1つ出るまでに何が起きているかを、順番に、数式まで含めて記録します。

---

## 全体の流れ

```
1. 取得    59系列（日本株22 + 海外指標37）をProviderから取る
2. 選別    08:30 JSTより前に利用可能だったデータだけを残す
3. 特徴量  価格・金利から予測材料を作る
4. 学習    銘柄ごとに直前120営業日で2つのモデルを訓練
5. 予測    当日の材料を入れてリターンと上昇確率を出す
6. 判定    BUY条件を満たすか決める
7. 保存    22銘柄まとめて1つの単位として公開
```

各段階で「未来の情報が混ざっていないか」を検査します。1つでも混ざれば保存を拒否します。

---

## 1. 取得

`data/fetch.py` が59系列を **1つずつ順番に** 取ります。並列にするとProviderのレート制限に当たるためです。

各行に3つの時刻を別々に記録します。ここがこのシステムの背骨です。

| 列 | 意味 |
|---|---|
| `available_timestamp` | その値が世に出た時刻（市場の終値時刻＋Provider遅延） |
| `first_observed_at` | このシステムが初めて観測した時刻 |
| `retrieved_at` | 実際に取得した時刻 |

1つの時刻では足りません。「公表は昨日18時だが、システムが実際に手にしたのは今朝9時」という差を区別しないと、後から取ったデータを「当時持っていた」ことにできてしまいます。

---

## 2. 選別（Look-Ahead防止）

予測日 `t` の締切は **`t` の 08:30 JST 固定**です。実行が遅れても動かしません。

特徴量に採用できるのは、次を **すべて** 満たす行だけです。

```
available_timestamp  <= 08:30 JST
first_observed_at    <= 08:30 JST
retrieved_at         <= 08:30 JST
```

1つでも超えていれば `database/repository.py` の `add_feature_input` が例外を投げ、その予測は保存されません。

```
ValueError: raw input was not observed by the prediction cutoff
```

**過去日を指定した手動実行が必ず失敗するのはこのためです。** データを取ったのが後日なら、`retrieved_at` が締切を超えます。これは不具合ではなく、設計どおりの拒否です。

---

## 3. 特徴量

### 価格から作るもの（11個）

`features/builder.py`。`C` は終値、`O` は始値、`H` は高値、`L` は安値。

| 特徴量 | 式 |
|---|---|
| `return_1d` … `return_20d` | `C_t / C_{t-n} - 1`（n = 1, 2, 3, 5, 20） |
| `log_return_1d` | `ln(C_t / C_{t-1})` |
| `volatility_5d` / `volatility_20d` | 1日リターンの標準偏差（5日 / 20日、ddof=1） |
| `open_close_return` | `C_t / O_t - 1` |
| `high_low_range` | `H_t / L_t - 1` |
| `ma20_deviation` | `C_t / MA20_t - 1` |

分母が0や欠損なら `NaN` にします。0で埋めると「変化なし」という誤った情報を与えるためです。

### 米国金利から作るもの

`data/treasury_features.py`。2年・10年・30年の水準に加えて次を作ります。

```
10Y-2Y スプレッド = US10Y - US2Y
30Y-10Y スプレッド = US30Y - US10Y
n日変化 = 当日の利回り - n営業日前の利回り   （n = 1, 3, 5）
```

派生値の `available_timestamp` は、**元になった値のうち最も遅いもの**を引き継ぎます。片方が古ければ、派生値も古い扱いになります。

### 重要: 同日の値は使えません

`open_close_return` は `C_t / O_t - 1` で、**これは予測対象そのもの**です。同じ行の特徴量をそのまま使えば、答えを見せて予測させることになります。

- **本番**（`services/dataset.py`）: 締切時刻で機械的に切るため、当日の終値は構造上入りません
- **検証**（`scripts/run_week_test.py`）: 自銘柄の価格特徴量と海外指標を **1営業日ラグ** させています

---

## 4. 学習

銘柄ごとに独立して、**予測日の直前120営業日**だけで訓練します（`config/model.yaml` の `window_jpx_sessions`）。

### 前処理

scikit-learnのPipelineとして組み、**学習用の分割の中だけで**適合させます。

```
欠損補完（中央値） → 標準化（StandardScaler） → モデル
```

Pipelineにしているのは、交差検証の各分割で前処理が自動的に再適合されるからです。全期間で標準化してしまうと、未来の平均と分散が学習に漏れます。

### 2つのモデル

| 目的 | モデル | 出力 |
|---|---|---|
| 予測リターン | **Ridge回帰** | `predicted_return` |
| 上昇確率 | **ロジスティック回帰** | `probability_up` |

Ridgeの目的関数:

```
最小化   ||y - Xw||²  +  α||w||²
```

`α` は `TimeSeriesSplit`（5分割）で選びます。候補は `[0.01, 0.1, 1.0, 10.0, 100.0]`。分割は必ず時系列順で、ランダム分割は使いません。

学習対象 `y` は次のとおりです。

```
y = 当日終値 / 当日始値 - 1        （日中リターン）
```

ロジスティック回帰は `y > 0` を1、それ以外を0とする二値分類です。

**ElasticNet / Lasso / OLS** も実装済みですが診断用で、本番はRidge固定です。同じ窓で順位付けした結果をそのまま成績として報告すると選択バイアスになるため、自動昇格はしません。

---

## 5. 予測

当日の特徴量1行を、学習済みモデルに入れます。

```
predicted_return = w · x_today + b
probability_up   = 1 / (1 + exp(-(w' · x_today + b')))
```

価格に直すときは2種類あります。**これを混ぜてはいけません。**

| 時点 | 式 | 使う場面 |
|---|---|---|
| 朝（08:30時点） | `前日終値 × (1 + predicted_return)` | 寄り付きが未確定なので前日終値を基準にする |
| 寄り付き後 | `実際の寄値 × (1 + predicted_return)` | 実際の寄値が判明してから引き直す |

1列にまとめると「寄り付きを知った上で予測した」ように見えるため、ダッシュボードでは両方を並べています。

---

## 6. BUY判定

```
BUY  ⟺  predicted_return > 0.003  かつ  probability_up >= 0.60
```

両方を同時に満たす必要があります。片方だけでは買いません（`config/trading.yaml`）。

株数は板の単位に合わせます。

```
株数 = floor(投資額 / (寄値 × (1 + 手数料率)) / 100) × 100
```

損益（`trading/strategy.py`）:

```
約定買値 = 寄値 × (1 + スリッページ率)
約定売値 = 終値 × (1 - スリッページ率)
手数料   = (買約定代金 + 売約定代金) × 手数料率
損益     = (終値 - 寄値) × 株数 - スリッページ - 手数料
```

スリッページは買いと売りの**両方を不利な方向**に動かします。初期値は手数料・スリッページとも片側5bps、1銘柄100万円、100株単位です。

### 除外条件

決算発表の前後は、株価が決算内容で動くため、この仕組みの対象外にします（`trading/earnings.py`）。

- 除外範囲: **発表日とその前後1営業日**（計3営業日）
- 日本企業は大引け後に発表するため、反応するのは翌営業日
- 土日はまたがず、営業日で数える（金曜発表 → 月曜を除外）

決算発表日は数週間前に公表されるため、これを使うことはLook-Aheadに当たりません。**発表の中身は一切読みません。**

---

## 7. 保存

22銘柄を **1つの `PredictionSet` としてまとめて** 公開します。銘柄ごとにバラバラに公開しません。半分だけ成功した状態を「その日の予測」として見せないためです。

取得に失敗した銘柄は、未来の値で埋めず `INSUFFICIENT_DATA` として記録します。

保存する内容:

- 予測値、上昇確率、予測区間、判定、順位
- 使用したモデルの係数、切片、標準化のパラメータ
- 学習期間、学習サンプル数、選ばれたハイパーパラメータ
- 元になった生データ1行1行へのリンク（誰がいつ取得したか）

最後の項目により、**どの予測がどの生データから来たかを後から完全に追跡できます**。

---

## 8. 評価（大引け後）

15:45以降に実際の値を取得し、答え合わせをします。

```
実績リターン = 実際の終値 / 実際の寄値 - 1
方向的中     = (predicted_return > 0) == (実績リターン > 0)
```

集計指標（すべてOut-of-Sampleのみ）:

```
勝率           = 勝ちトレード数 / 全トレード数
Profit Factor  = 勝ち金額の合計 / 負け金額の合計
Expectancy     = 勝率 × 平均勝ち額 - 敗率 × |平均負け額|
Sharpe         = 平均リターン / 標準偏差 × √252
Sortino        = 平均リターン / 下方偏差 × √252
最大DD         = max((ピーク - 谷) / ピーク)
MAE            = mean(|予測 - 実績|)
RMSE           = √(mean((予測 - 実績)²))
```

**20トレード未満は `LOW_SAMPLE` として警告します。** 少数の勝率は偶然で大きく動き、判断材料になりません。

## 計算にかかる時間

処理そのものは軽く、時間の大半は通信です。

| 工程 | 時間 |
|---|---|
| 59系列の取得（家庭回線） | 約1.5分 |
| 59系列の取得（GitHub Actions） | **25〜35分** |
| 特徴量の生成 | 数秒 |
| 22銘柄の学習と予測 | 2〜4分 |
| 保存（ローカルDB） | 数秒 |
| 保存（Neon・シドニー） | 数分 |

GitHub Actionsが遅いのは、Yahooが**データセンター由来のIPを厳しく絞る**ためです。家庭回線では1系列1.4秒、Actionsでは25〜35秒と20倍以上の差があります。アクセス回数の問題ではなく接続元の問題なので、時間を置いても解消しません。

対策として、予測の開始を07:00 JSTに前倒し（メールまで105分の余裕）、タイムアウトを60分に拡大しています。

根本対策は「**DBが既に持っている系列は取りに行かない**」ことです。期間を短くしてもリクエスト数は減りません（1系列＝1リクエスト）。減らせるのは系列そのものをスキップしたときだけです。
